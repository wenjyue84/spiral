## Iteration [22] - Story: US-1413 Phase V: Auto-Extract Verifiable Assertions from Story Acceptance Criteria

### What was implemented

Created a complete system for automatically extracting and validating assertions from acceptance criteria:

1. **lib/assertion_extractor.py (309 lines)**
   - Pattern-based parser for natural language assertions
   - Supports 4 assertion patterns: "assert X", "must have Y", "should return Z", "contains [item]"
   - Assertion namedtuple with type, subject, expected_value, confidence_score fields
   - Auto-generates pytest assertion code to .spiral/auto_assertions/<story-id>.py
   - CLI interface for command-line usage
   - Full type hints (passes mypy strict)

2. **tests/test_assertion_extractor.py (318 lines)**
   - 23 comprehensive unit tests covering:
     - Pattern extraction for each assertion type
     - Confidence scoring
     - Pytest code generation
     - Edge cases (special characters, case insensitivity, punctuation)
     - Integration tests (extract → generate workflow)
   - All tests passing

3. **lib/phases/phase_v_validate.sh (40 lines added)**
   - New auto-generation section before AC Verification
   - Checks if stories have explicit testFiles/testMarker in verification field
   - Calls assertion_extractor for stories without explicit verification
   - Generates .spiral/auto_assertions/<story-id>.py files
   - Uses SPIRAL_AUTO_ASSERTIONS config var (defaults to true)
   - Integrated with existing Phase V validation pipeline

### Patterns discovered

- Phase V already had infrastructure for AC verification (ac_assertion_extractor.py, ac_verification_runner.py)
- This story complements that by adding auto-generation for stories without explicit verification contracts
- The regex-based approach works well for clean AC text but struggles with vague/descriptive AC
- Confidence scoring helps distinguish high-confidence vs low-confidence extractions

### Gotchas

- AC text needs to follow specific patterns for extraction to work
- Quoted items in AC text can confuse the regex patterns (matching internal quotes)
- The assertion_extractor.py is a simpler, pattern-focused extractor separate from ac_assertion_extractor.py
- SPIRAL_AUTO_ASSERTIONS config variable needed to be used consistently with Phase V conventions

## Iteration [23] - Story: US-1419 Integration test: Phase S merges federated stories with namespace validation

### What was implemented

Created comprehensive integration test for Phase S federated story merging with namespace preservation:

1. **tests/test_phase_s_integration_federated.py (224 lines)**
   - Test fixtures for temporary PRD structure (main prd.json + sub/payments/prd.json)
   - Fixtures for main PRD data (5 stories) and payments sub-project data (3 stories, 1 duplicate)
   - Main test function: `test_federated_story_merge_with_namespace()`
   - Validates all 3 acceptance criteria:
     - AC1: Story count after merge (8 total: 5 from main + 3 from payments)
     - AC2: Duplicate detection finds US-25 vs US-3 pair with score >= 0.75 (achieved 0.97!)
     - AC3: Namespace preservation via sub_project field and ID routing

### How it works

- Uses `lib.federated_merge_prd.merge_prds()` to merge multiple PRD files
- Uses `lib.phase_s.duplicate_detector.find_duplicates()` for similarity detection
- Merges treats each project directory as a namespace source
- Each merged story gets a `sub_project` field indicating its origin (main or payments)
- Duplicate detection uses sentence-transformer embeddings (all-MiniLM-L6-v2 model)
- Embedding cache prevents recomputation across test runs

### Patterns discovered

- Phase S is responsible for story validation (constitution, goals), not merge
- Federated merge happens earlier in the pipeline (likely phase-specific preprocessing)
- Duplicate detection uses embedding-based similarity (0.75 threshold by default)
- Story namespace is preserved via `sub_project` field (used by Phase M/X for routing)
- Merging 5 + 3 stories produces 8 total; deduplication is Phase M's responsibility
- Similarity scoring works well: US-25 ("Payment gateway integration") vs US-3 ("Gateway payment integration") achieved 0.97 score

### Gotchas

- `federated_merge_prd.merge_prds()` returns a tuple of (merged_prd, errors), not just merged_prd
- Story namespace is stored in `sub_project` field, not as ID prefix (different from load_with_includes())
- Embedding model download happens on first run (one-time ~100MB download for all-MiniLM-L6-v2)
- Duplicate pairs are found regardless of order; need to check both directions
- Test uses test-specific story data to ensure reproducible duplicate detection
