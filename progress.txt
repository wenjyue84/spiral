
## Pre-analysis for US-782 (Gemini 2.5 Pro)
### Technical Brief: US-782 Blame Attribution

**Objective:** Correlate newly failing tests with the story and specific file changes that introduced them.

**Affected Files & DocTypes:**
*   **`spiral.sh`:** The main orchestrator. A new section, "Phase V", will be added.
*   **`lib/test_blame.py`:** A new Python script to house the core attribution logic.
*   **No Frappe DocTypes are involved.** The system appears to be a custom CI/dev tool, not an ERPNext app. The primary data structure is the story JSON file itself.

**Implementation Plan:**
1.  **`spiral.sh` - Baseline Capture (Pre-Phase I):**
    *   Execute the project's full test suite.
    *   Store the raw test results (pass/fail status for each test) in a baseline file: `.spiral/test_baseline.json`.

2.  **`spiral.sh` - Attribution (Phase V):**
    *   After the implementation and post-change test run are complete, invoke `lib/test_blame.py`.
    *   Pass the script the paths to the baseline results, the new results, and the list of files modified by the story (obtained from `git diff`).
    *   The script will return a list of newly failed tests and the likely source file.
    *   Update the story's `_failureReason` field with the failing test names.

3.  **`lib/test_blame.py` - Core Logic:**
    *   The script will parse both test-result files to identify tests that passed in the baseline but failed in the new run.
    *   It will correlate a failing test (e.g., `test_foo.py`) to a changed source file (e.g., `lib/foo.py`) based on a naming convention.

**Gotchas & Edge Cases:**
*   The attribution logic assumes a clear naming convention between test files and source files.
*   Flaky tests appearing in the new run could be incorrectly attributed to the story.
*   A single file change may break numerous unrelated tests, which could create noisy attribution reports.
