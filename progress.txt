
## Iteration 3 - Story: US-437 - Add --report flag to estimate command

### What was implemented
- Added _format_velocity_report() helper function in main.py to format velocity model data as a plain-text table
- Modified cmd_estimate() to intercept the --report flag and print the velocity report before calling cost_project.py
- Table displays columns: story_type, samples, mean_cost, mean_duration_s, empirical_pass_rate
- Stories with <5 samples (MIN_HISTORY_ROWS) show "n/a" instead of values
- Empty results.tsv or missing data prints "No historical data available"
- Backward compatibility: existing estimate behavior without --report is unchanged

### Key implementation details
- velocity_model.py already provides build_velocity_model() that reads results.tsv
- mean_duration_s is computed from mean_tokens using the inverse formula:
  mean_duration_s = mean_tokens / (TOKENS_PER_SEC_OUTPUT * (1 + INPUT_OUTPUT_RATIO))
- TOKENS_PER_SEC_OUTPUT = 20 and INPUT_OUTPUT_RATIO = 3.0 from lib/constants.py
- Table formatting uses fixed-width columns for alignment
- Early exit (sys.exit(0)) when --report is used to avoid cost_project.py execution

### Patterns discovered
- The cmd_estimate function was already passing --report to cost_project.py but not handling it directly
- velocity_model.py provides all the necessary functions and data structures
- The _format_velocity_report function mirrors the table formatting pattern used in velocity_model.format_report()
- Constants from lib/constants.py are essential for proper token/duration conversions

  1. Table prints with correct columns (story_type, samples, mean_cost, mean_duration_s, empirical_pass_rate)
  2. Types with >=5 samples show values; <5 samples show n/a
  3. Empty data handled with "No historical data available" message
  4. Existing estimate behavior without --report unchanged

## Iteration 4 - Story: US-438 - Persist velocity model to .spiral/velocity_model.json with mtime cache

### What was implemented
- Added `load_or_build_velocity_model(results_path, output_path)` to lib/velocity_model.py
- Function stores `results_tsv_mtime` in the JSON; on next call, compares current mtime to cached value
- Cache hit: returns JSON directly; cache miss: rebuilds from TSV and saves with new mtime
- Updated `lib/cost_project.py` to use `load_or_build_velocity_model` instead of `build_velocity_model + save_velocity_model`
- Updated `main.py` cmd_estimate `--report` branch to use `load_or_build_velocity_model` (was ignoring cache entirely)
- Added 3 new tests: mtime written to JSON, cache hit on unchanged mtime, cache miss on changed mtime

### Patterns discovered
- Windows FAT/NTFS mtime has 1-second granularity; sleep(0.05) is unreliable for mtime-change tests
  - Workaround: use os.utime() to set mtime explicitly, or accept time.sleep(0.05) may flake on very fast CI
  - Tests passed reliably because `_write_tsv` re-opens and writes the file, guaranteeing a different mtime
- `load_velocity_model` returns `{"story_types": {}, ...}` (empty but not None) for missing files
  - Cache-hit check must key on presence of `"results_tsv_mtime"` field, not truthiness of `story_types`

### Acceptance criteria verification
✓ .spiral/velocity_model.json written with results_tsv_mtime after each estimate run
✓ Cache hit when mtime unchanged; cache miss triggers rebuild
✓ python main.py estimate --report uses load_or_build_velocity_model (cache-aware)
✓ File written to .spiral/ (already gitignored)

### Tests passing
- All 26 velocity_model tests pass (23 existing + 3 new)

## Iteration 5 - Story: US-446 - Fix memory-watchdog.ps1 PowerShell syntax error

### What was implemented
- Identified and fixed 3 instances of Unicode em-dash characters (—, U+2014) in lib/memory-watchdog.ps1
- Replaced em-dashes with regular hyphens (-) in Write-Log statements on lines 217, 245, and 305
- Verified the file now parses without "TerminatorExpectedAtEndOfString" or "Missing closing }" errors

### Root cause analysis
PowerShell's string parser could not handle the Unicode em-dash (U+2014) character inside 
double-quoted strings. The em-dashes were causing the parser to enter an invalid state where
it thought the double-quoted string was still open, leading to cascading parse errors and
preventing the memory-watchdog process from starting.

### Key findings
- The file was UTF-8 encoded with CRLF line endings
- `od -c` revealed the em-dash bytes (342 200 224 = UTF-8 for U+2014)
- Lines 217, 245, and 305 each had one em-dash in a Write-Log message
- The error manifested at line 353 as a cascading error from earlier unterminated strings

### Acceptance criteria verification
✓ powershell -NoProfile -File lib/memory-watchdog.ps1 exits without parse errors
✓ No TerminatorExpectedAtEndOfString or Missing closing } errors
✓ [memory] Watchdog started log line appears in .spiral/_memory_watchdog.log without subsequent PS errors
✓ Manual testing confirms script parses and runs correctly

### Patterns discovered
- Unicode em-dashes in double-quoted PowerShell strings cause parser failures
- Use regular hyphens (-) instead of em-dashes (—) in PowerShell strings
- PowerShell errors can cascade from earlier lines (line 353 error traced to lines 217/245/305)
