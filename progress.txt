## Pre-analysis for US-1425 (Gemini 2.5 Pro)
This is a technical brief for implementing story `US-1425` in the Spiral project.

**Note:** The user story is for the Spiral codebase and involves `bash` scripts, not a Frappe/Python application.

**1. Files to Modify/Create:**

*   **Modify:** `lib/run_parallel_ralph.sh`
*   **Create:** `lib/impl/worker_monitor.sh`
*   **Reference (for testing):** `tests/test_worker_monitor.bats`, `tests/test_worker_stall.py`

**2. Involved Components:**

*   This task does not involve any Frappe DocTypes or hooks.
*   It modifies the core worker execution logic in the Spiral agent system.

**3. Implementation Approach:**

*   In `lib/run_parallel_ralph.sh`, when a worker process is started, also spawn `lib/impl/worker_monitor.sh` as a background process (`&`). Pass the worker's PID, ID, and story file path as arguments.
*   Create `lib/impl/worker_monitor.sh` with a `while true` loop that sleeps for 30 seconds.
*   Inside the loop, get the modification time of the worker's heartbeat file (e.g., `.spiral-workers/worker-1/_heartbeat`).
*   If the time since the last update exceeds `SPIRAL_WORKER_STALL_TIMEOUT_SECONDS` (env var, default 90s), the script should:
    1.  Log a stall alert.
    2.  Kill the stalled worker's PID.
    3.  Restart the worker with its original story (read from `_story.json`).
    4.  Append a JSON object `{"event": "worker_stalled_and_recovered", ...}` to `spiral_events.jsonl`.
    5.  Exit the monitor script, as the parent will launch a new one for the new worker.

**4. Edge Cases & Gotchas:**

*   **PID Management:** Ensure the monitor script reliably gets the correct worker PID and terminates itself after a restart.
*   **Race Conditions:** A worker might complete just as the monitor decides to kill it. Check if the process exists before issuing `kill`.
*   **Atomic Logging:** Writing to `spiral_events.jsonl` from multiple monitors could cause corruption. Use a file-locking mechanism if possible, though simple append (`>>`) may suffice.
