

## Pre-analysis for US-1134 (Gemini 2.5 Pro)
Here is a technical brief for implementing story US-1134.

**Objective:** Implement a warning and automatic threshold fallback mechanism in the "Phase M" story merge process when all candidates are rejected.

**1. Files to Modify:**
*   `lib/merge_stories.py`: Core logic for the merge process, state tracking, and threshold adjustment.
*   `spiral.config.sh`: To add the new `SPIRAL_DEDUP_FALLBACK_ITERS` configuration variable.
*   `tests/test_merge_stories.py`: To add unit tests for the new warning and fallback logic.

**2. Involved Components:**
*   This is a Python script, not a Frappe application.
*   The main process is orchestrated within `lib/merge_stories.py`.
*   Configuration is controlled by environment variables sourced from `spiral.config.sh`.

**3. Implementation Approach:**
*   Introduce a state-tracking mechanism (e.g., a simple counter in a temp file) to record consecutive iterations with zero new stories.
*   In `merge_stories.py`, after the merge attempt, check if `new_stories_added == 0` and `input_candidates > 0`.
*   If true, increment the consecutive failure counter and emit the required `WARNING` log.
*   If false, reset the counter to zero.
*   Before the next merge's deduplication logic, check if the counter has reached `SPIRAL_DEDUP_FALLBACK_ITERS`. If so, temporarily lower the semantic deduplication threshold by 0.05 for that single run.

**4. Edge Cases & Gotchas:**
*   **State Persistence:** The failure counter must persist across separate runs of the script.
*   **Threshold Floor:** The fallback threshold must not go below `0.60`.
*   **One-Time Fallback:** The lowered threshold is temporary for one iteration only; it should not permanently alter the base threshold.
*   **Disabling:** The fallback logic should be skipped if `SPIRAL_DEDUP_FALLBACK_ITERS` is set to 0.

## Pre-analysis for US-1136 (Gemini 2.5 Pro)
Based on the user story, here is a technical brief for the agent:

### **To-Do: Implement Locked TSV Appending (US-1136)**

This brief outlines the plan to fix a race condition where parallel workers corrupt `results.tsv`. The user story content overrides the initial prompt's mention of Frappe; this is a Python/shell script task.

**1. Primary Files to Modify:**
*   `ralph/ralph.sh`: The core worker script likely containing the `>> results.tsv` redirection that needs replacement.
*   `lib/run_parallel_ralph.sh`: The orchestrator script that runs multiple `ralph.sh` workers; may also contain result-handling logic.

**2. Key Concepts & New Files:**
*   **New File:** Create a new shell script helper: `lib/core/locked_append_tsv.sh`.
*   **Core Logic:** This script will use `flock` for exclusive file locking to prevent concurrent writes from interleaving.

**3. Recommended Implementation Approach:**
1.  **Create `lib/core/locked_append_tsv.sh`:**
    *   It should accept the target file path and the data to append as arguments.
    *   Use `flock -x <lock_file> -c "printf '%s\\n' ... >> <target_file>"` to wrap the append operation.
    *   The lock file path should be derived from the target file (e.g., `results.tsv.lock`) and be local to the worker's environment to avoid cross-run contention.
2.  **Refactor `ralph.sh`:**
    *   Find all instances of `printf ... >> results.tsv` or `echo ... >> results.tsv`.
    *   Replace them with a call to the new helper, e.g., `lib/core/locked_append_tsv.sh "$RESULTS_TSV_PATH" "$tsv_data_row"`.
3.  **Verification:**
    *   Create a temporary test script that launches several background workers to append lines simultaneously and verify the output TSV file has no garbled lines.

**4. Edge Cases & Gotchas:**
*   **`flock` Availability:** Ensure `flock` is available in the target execution environment (it is standard on Linux).
*   **Lock Scope:** The lock must be worker-local (per worktree), not global. Do not use a single lock file in `/tmp`. The path to the lock should be relative to the worker's output directory.
*   **Performance:** The lock should be held for the shortest possible duration. The `flock -c` pattern is efficient and handles this well.
*   **Error Handling:** While `flock` automatically releases the lock on exit, ensure the calling script (`ralph.sh`) is robust to failures during the append.

## Implementation for US-1136 (Claude Haiku 4.5)

**What was implemented:**
- Created `lib/core/locked_append_tsv.sh`: Shell wrapper using mkdir-based atomic file locking
- Created `lib/core/locked_append_tsv.py`: Python implementation with fcntl (POSIX) and msvcrt (Windows) support
- Modified `lib/run_parallel_ralph.sh` line 1516: Replaced raw `>> "$WTREE/results.tsv"` with `locked_append_tsv "$WTREE/results.tsv" "$_timeout_row"`
- Added test suite: `tests/test_locked_append_tsv.sh`, `tests/test_locked_append_overhead.sh`, `tests/test_locked_append_latency.sh`

**Patterns discovered:**
- Only one raw `>> results.tsv` append exists in the codebase (timeout handler in run_parallel_ralph.sh)
- ralph.sh does not directly write results.tsv (only run_parallel_ralph.sh manages it)
- mkdir-based atomic locking is simpler and more portable than flock on Windows
- Windows filesystem operations (mkdir/rmdir) have ~95ms latency, exceeding the 50ms budget

**Acceptance Criteria Met:**
- ✓ Exclusive file lock before appending (mkdir atomic operation)
- ✓ All >> results.tsv replaced with locked_append_tsv
- ✓ Lock is released even if append fails (atomic rmdir in shell handler block)
- ✓ Concurrent writes (3 workers × 5 rows) produce clean TSV with zero corruption
- ⚠ Append latency overhead ~68ms on Windows (exceeds 50ms target due to filesystem operations, not implementation)

**Gotchas & Notes:**
- mkdir-based locking chosen over flock because flock is unreliable on Windows Git Bash
- Python helper provided as fallback for systems where mkdir doesn't work well
- Windows filesystem latency is the limiting factor; no pure-shell solution can be faster
- The 50ms budget is likely unachievable on Windows without using OS-level primitives
- Lock is worker-local (per WTREE) as required, avoiding cross-run contention


## Pre-analysis for US-1137 (Gemini 2.5 Pro)
### Technical Brief for US-1137: Atomic prd.json Updates

**Objective:** Prevent race conditions when concurrent shell processes update `prd.json` within the same worker worktree by introducing a locking mechanism. This is a shell scripting task, not a Python/Frappe task.

**Affected Files:**
*   **Create:** `lib/core/prd_lock.sh`
*   **Modify:**
    *   `lib/run_parallel_ralph.sh`
    *   `lib/impl/retry.sh`
    *   `lib/impl/decompose.sh`
    *   `lib/impl/commit_revert.sh`

**Involved Frappe/Framework Components:**
*   None. This task is confined to shell scripts and does not interact with Frappe DocTypes or hooks.

**Implementation Approach:**
1.  **Create `atomic_patch_prd()`:** In a new `lib/core/prd_lock.sh` file, implement a shell function `atomic_patch_prd <wtree> <jq-filter>`.
2.  **Locking:** Use `mkdir` to create a lock directory (e.g., `<wtree>/prd.json.lock`). This is an atomic operation. Store the current PID inside the lock directory for debugging.
3.  **Read-Modify-Write:** The function will read the target `prd.json`, apply the `$2` (jq filter) to it in memory, and write the result to a temporary file.
4.  **Atomic Write:** Use `mv` to atomically replace the original `prd.json` with the temporary file.
5.  **Refactor Existing Code:** Replace all `jq ... > prd.json.tmp && mv prd.json.tmp prd.json` patterns in the affected scripts with a call to `atomic_patch_prd`.

**Edge Cases & Gotchas:**
*   **Stale Locks:** The lock mechanism must handle stale locks. Implement a cleanup that removes locks older than 60 seconds.
*   **Concurrency:** The solution must be tested to ensure it correctly serializes concurrent writes. The AC specifies a test of 10 parallel appends.
*   **Timeouts:** Lock acquisition should time out after 30 seconds and exit with a clear error message.
*   **Cleanup:** Ensure the lock directory is always removed on successful exit or when a timeout occurs.


## Iteration N - Story: US-1137 - Parallel workers: atomic compare-and-swap for prd.json updates

### What was implemented
- Created `lib/core/prd_lock.sh` with `atomic_patch_prd <wtree> <jq-filter> [extra-jq-args...]`
- Replaced 2 bare jq patterns in `lib/run_parallel_ralph.sh` (lines 790, 1641-1642)
- Replaced 1 bare jq pattern in `lib/impl/retry.sh` (anti-pattern accumulation)
- `lib/impl/decompose.sh` and `lib/impl/commit_revert.sh` had no bare jq patterns (Python handles their writes)
- Added `tests/prd_lock.bats` with 5 tests including 10-concurrent-append serialization

### Patterns discovered
- Stale lock detection via directory mtime (_dir_mtime uses GNU stat -c %Y / BSD stat -f %m) avoids the race between mkdir and file write that plagued the original approach
- Check staleness ONCE before the spin loop, not inside it — checking inside allows processes to see empty `created` file and falsely remove valid locks
- `atomic_patch_prd` takes jq extra args AFTER the filter: `atomic_patch_prd <wtree> <filter> --arg key val`
- `prd_lock.sh` is sourced in `run_parallel_ralph.sh` alongside `locked_append_tsv.sh` using the same SPIRAL_HOME pattern
- In `retry.sh` (no SPIRAL_HOME var), use `${SPIRAL_HOME:-$(dirname "${BASH_SOURCE[0]}")/../..}` fallback

### Gotchas
- BASH_SOURCE path gives `lib/impl`, so `../..` reaches repo root for prd_lock.sh path
- decompose.sh and commit_revert.sh satisfy the AC trivially (no patterns to replace)
- bats test for stale lock must use `touch -t 197001010000 dir` to backdate mtime, not a `created` file
