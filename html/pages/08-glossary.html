08 Glossary

Terminology and definitions
C D E F G I M P R S V W
C
Capacity Limit
The maximum number of pending (unimplemented) stories SPIRAL keeps in prd.json at any time, controlled by SPIRAL_MAX_PENDING. When the limit is reached, Phase M skips merging new candidates until existing stories are completed.
See also: PRD, SPIRAL_MAX_PENDING
Constitution
A Markdown file (constitution.md) that defines non-negotiable quality standards every story must satisfy before it is merged into the backlog. Phase S validates each candidate against the constitution and rejects stories that violate its rules.
See also: Story, Phase S — Story Validate
Cost Ceiling
An optional per-session or per-story API spending limit (SPIRAL_COST_CEILING) that halts SPIRAL when cumulative cost exceeds the threshold. Protects against runaway API spend during unattended runs.
See also: Model Routing, SPIRAL_COST_CEILING
D
Decompose
The process in Phase I where an oversized story is automatically split into two or more smaller sub-stories so that each fits within a single Ralph worker context window. The parent story is marked _decomposed: true and the children carry a _decomposedFrom reference.
See also: Story, Ralph, Phase I — Implement
DLQ (Dead-Letter Queue)
Stories that have exhausted all retry attempts (default 3) without passing are moved to the Dead-Letter Queue and skipped for the remainder of the run. They are preserved in prd.json with passes: false so they can be investigated and re-queued manually.
See also: Story, Iteration, Configuration
E
Episodic Memory
An optional learning layer (SPIRAL_EPISODIC_MEMORY=true) that appends per-story outcome records to .spiral/episodic_memory.jsonl after each iteration. Phase E queries these records to surface implementation patterns that worked for similar stories, surfacing them as enrichment.past_patterns hints to Ralph.
See also: Ralph, Iteration, SPIRAL_EPISODIC_MEMORY
F
Focus
A per-session theme set in Phase 0-B (e.g., "improve dashboard UX") that biases story selection and implementation toward a particular area. The focus string is injected into Ralph's task prompt so workers prioritize approaches aligned with the current theme.
See also: Iteration, Ralph, Quick Start
G
Gate
A checkpoint in the SPIRAL loop (Phase G) where a human can review pending stories before implementation begins. Gates can be set to interactive (pause and prompt), proceed (auto-approve), or skip (bypass entirely) via the --gate CLI flag.
See also: Phase, CLI Reference
I
Iteration
One complete pass through the SPIRAL phase loop — from Phase A (AI Suggest) through Phase L (Learning). Each iteration selects, validates, enriches, and implements one or more stories, then runs quality gates before looping back. The number of iterations is the first positional argument to spiral.sh.
See also: Phase, Story, Architecture
M
Model Routing
The strategy SPIRAL uses to select which Claude model tier (haiku → sonnet → opus) a story is implemented with, controlled by SPIRAL_MODEL_ROUTING. In auto mode the cheapest capable model is tried first and escalated on retry; SPIRAL_HISTORY_ROUTING=true additionally consults historical pass rates to pick the optimal tier.
See also: Ralph, Cost Ceiling, SPIRAL_MODEL_ROUTING
P
Phase
One discrete stage in the SPIRAL loop, labelled 0 through L (e.g., Phase A: AI Suggest, Phase I: Implement). Phases execute in a fixed order each iteration; some pairs run in parallel (Phase R and Phase T). Phase logic lives in spiral.sh with stubs in lib/phases/.
See also: Iteration, Architecture, Phase Deep-Dive
PRD (Product Requirements Document)
The prd.json file that is SPIRAL's source of truth for the product backlog. Each entry is a user story with acceptance criteria, priority, and status. Phases A, R, T, and M write to the PRD; Phase I reads from it to select work.
See also: Story, Capacity Limit, Introduction
R
Ralph
The autonomous implementation agent that executes a single story inside SPIRAL. Ralph is invoked by ralph/ralph.sh, which spawns a Claude CLI process with a carefully constructed prompt (ralph/CLAUDE.md). Each Ralph invocation handles exactly one story: plan, implement, quality-check, commit, and exit.
See also: Worker, Worktree, Architecture
S
Story
A single unit of work in prd.json, identified by a US-NNN or UT-NNN ID. A story carries a title, description, acceptance criteria, filesTouch hints, and a passes flag that Ralph sets to true on successful completion. Stories are atomic and must have no hidden co-dependencies.
See also: PRD, Decompose, Constitution
V
Validate Cmd
The shell command configured in SPIRAL_VALIDATE_CMD (e.g., uv run pytest tests/) that Phase V runs after each implementation to verify the full test suite still passes. Stories without a dedicated verification field fall through to this command as a catch-all gate.
See also: Phase, SPIRAL_VALIDATE_CMD, Phase V — Validate
W
Worker
A parallel Ralph instance managed by lib/run_parallel_ralph.sh. Each worker runs in its own git worktree and processes one story slice simultaneously with other workers. The number of active workers is capped by SPIRAL_RALPH_WORKERS (default 1) to stay within memory budgets.
See also: Ralph, Worktree, SPIRAL_RALPH_WORKERS
Worktree
An isolated git working directory created by git worktree add under .spiral-workers/worker-N/ for each parallel Ralph worker. Worktrees share the same object store as the main repo but have independent working trees, preventing workers from clobbering each other's changes.
See also: Worker, Ralph, Architecture
